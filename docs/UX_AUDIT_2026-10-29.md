# UX and visual audit — 29 October 2026

Implementation follow-up (30 October): the concrete interface changes below have been
implemented; see [delivered behavior](SPEC.md#shared-interface-and-discovery) and
[CHANGELOG](CHANGELOG.md). This document retains the original findings and baseline
screenshots. Actual member research, physical-device/screen-reader and live external
integration validation remain outstanding; the recommendations are not a certification.

Audited revision: `ec69dee` (PR #126). This is an assessment and improvement backlog;
recommendations below are not delivered behavior or scheduled sprint commitments.

The application has useful, working member workflows and strong recent safeguards.
The largest remaining problems are task visibility on small screens, accessible form
names, inconsistent action hierarchy, and dense information presentation. A shared
component pass followed by the proposal and Admin journeys would deliver more value
than adding decorative effects.

## Scope and evidence

- Captured **48 page/locale/role states**: 24 each in English and Spanish, using an
  isolated database containing synthetic members, proposals, votes, orders and feedback.
- Inspected **72 Chromium renders**: every English state at 375 and 1280 CSS-pixel
  viewports, and every Spanish state at 375. This is phone-width emulation, not testing
  on physical iOS/Android devices. Desktop Chromium scrollbars reduce content width.
- Covered proposals/list/detail/create/edit, polls, Koins, group purchases/list/create/edit,
  Budget, Settings, Telegram linking, About, password change, QR confirmation/labels,
  login/registration, and six Admin sections: Members, Budget, Koins, Feedback, Errors,
  Settings. Reviewed templates, styles, routes and relevant service behavior.
- Also ran the existing real-browser keyboard/focus/dialog/hydration checks in both
  languages at 375/600/1280px. Those passed; accessibility gaps elsewhere remain.
- Collected DOM overflow, label associations, browser accessibility-tree names, small
  target candidates, canvas naming and heading counts. These are screening checks,
  not a WCAG conformance assessment. In particular, small inline links may qualify
  for target-size exceptions, and missing `h1` alone is not a WCAG failure.
- Empty/error/submission paths were reviewed in source and existing regressions;
  the screenshot sweep used populated read-only snapshots. Forms were not submitted
  to production. Browser/backend/SSO/Telegram live journeys and screen-reader sessions
  with actual members remain follow-up validation.
- QR artwork was previously decoder-checked; the screenshot sweep's static server did
  not serve dynamic QR image routes. Do not interpret those missing screenshot images
  as a live QR defect. Proposal image-alt observations are source findings, since the
  synthetic proposal examples deliberately had no uploaded images.

Measured results: **13 of 24 English phone-width states** contain at least one visible
field without an associated label/ARIA name; **7 of 24** contain genuinely unnamed
textbox/combobox/button nodes in Chromium's accessibility tree. Placeholder fallback
names account for some differences between the two measures. **13 of 24** lack an h1;
review overall landmark/heading structure rather than mechanically inserting headings.

Whole-document overflow was observed on proposal details: **420px content at a 375px
viewport in English, 409px in Spanish**. The other rendered states did not show measured
whole-document overflow. Contained tables can still be difficult to use despite passing
that check.

## Keep the improvements already delivered

- Shared dialogs already provide keyboard focus, Escape handling and focus return.
  Extend these components; do not reopen their completed implementation as new work.
- Navigation hydrates successfully in the local current build; active routes are named
  and the mobile menu has expanded/controls attributes.
- About now has the requested single reading column and sentence-level links. Preserve
  that preference; the remaining application should gain the same clarity and rhythm.
- Proposal drafts survive invalid images. Copy retries, money caps, actor attribution,
  error archives and private feedback notes provide valuable foundations.
- Chart date ranges, activity filters, Admin URL persistence, bilingual strings and
  QR confirmation already exist. Improve their discoverability rather than planning
  them again as missing features.

## Proposed visual direction

Keep a **single reading column** for About and forms. On phones, use one vertical path
through every task; data-heavy desktop surfaces may retain tables where they support
the task. Avoid nested cards whose borders carry no additional meaning.

| Element | Direction |
|---|---|
| Brand | Keep dark surfaces and yellow as the deliberate primary accent; use it more sparingly |
| Actions | Yellow primary, neutral secondary, accessible red destructive; colour is accompanied by labels |
| Typography | 16px body/input text; 14px metadata where appropriate; headings around 24–32px; line-height 1.5–1.65 |
| Money | Tabular numerals, clear signs and consistent currency grouping; colour supports the meaning rather than defining it |
| Spacing | Small shared scale: 4, 8, 12, 16, 24, 32px; roughly 16–20px card padding on phones, 24px desktop |
| Controls | Comfortable 44px target-height goal; restrained icon/remove controls with meaningful names; consistent focus/busy/disabled states |
| Status | One badge grammar for active/open/closed/approved/etc.; distinguish state, category and member action |
| Imagery | Show real proposal images when helpful; replace empty image blocks with a compact purposeful fallback or omit them |
| Tables | Dense only when needed; concise headers, wrapping, aligned numbers, contained scrolling and obvious row actions |
| Motion | Short, optional state transitions; preserve reduced-motion preferences as animation is introduced |

Concrete mobile proposal hierarchy:

1. Full proposal identity (up to two title lines) and amount.
2. One understandable state and author/date line.
3. Vote progress and the member's current choice.
4. Primary vote controls; secondary details/edit actions.

Concrete mobile feedback hierarchy:

1. Message preview + status/category.
2. Submitter/date/section in compact metadata.
3. Resolve/reject/review actions without horizontal scrolling.
4. Expandable admin notes/history/edit/delete with existing permissions and confirmation.

## Verification for follow-up work

- Prototype the proposal card and mobile feedback row first, using the screenshots above
  as baselines and the existing single-column About preference as a constraint.
- Include long titles/usernames, no-image and uploaded-image cases, empty/filter-empty
  states, long feedback, all statuses, large/signed monetary values and unlinked accounts.
- Test normal, hover, focus, disabled, busy, success and error states in both locales.
- Verify focus return and mobile navigation after form submissions, not only initial load.
- Keep money/state/idempotency/authorization behavior covered by existing regression packs.
  Add tests for newly changed behaviors; do not replace functional checks with source-only
  assertions or rewrite completed features merely to match this document.
- Confirm external SSO, Telegram linking/notification and actual QR scanning on real
  devices in an authorized test environment; those external flows were not exercised here.
